# خطة تطوير Tips CRM

> مبنية على ما ظهر فعلياً أثناء نشر الموقع وبناء تطبيق Android واختباره (أكتوبر 2026).
> الترتيب حسب الأولوية: لا نبني ميزات جديدة فوق أساس يُسقط بيانات المندوبين.

---

## الوضع الحالي باختصار

| المجال | الحالة | الدليل |
|---|---|---|
| الموقع | يعمل على `crm.tips-sd.com` (Node.js على Hostinger، نشر تلقائي من الفرع) | ✅ |
| تطبيق Android | يُبنى عبر EAS، كان يتوقف لحساب الشركة | أُصلح (قائمة المستخدم كانت تستخدم `localStorage` على الهاتف) |
| رفع الزيارات | **معطّل** | `null value in column "company_id" of relation "accounts"` — دوال قاعدة البيانات أقدم من عزل الشركات |
| قاعدة البيانات | ملفات SQL في المستودع **لا تطابق** القاعدة المنشورة | دوال مثل `tips_crm_save_visit_report` وأدوات المندوب الطبي غير موجودة في المستودع أصلاً |
| الأخطاء | تُخفى عن المستخدم | 14 موضعاً تعرض «حاول لاحقاً» بدل السبب الحقيقي؛ أخطاء Supabase ليست `Error` |
| المشرف والمدير | يقرآن الزيارات من ذاكرة الهاتف لا من الخادم | `app/supervisor/index.tsx` يعتمد على `data.visits` المحلية |
| الجودة | لا يوجد CI؛ 4 اختبارات تتصل بخدمات حقيقية وتفشل بدون مفاتيح | لا يوجد مجلد `.github` |
| الأمان | كلمة مرور موحدة لحسابات الاختبار مكتوبة في المستودع | `SYSTEM_GUIDE_AND_TEST_ACCOUNTS.md` |

## المرحلة 0 — تثبيت الأساس (أسبوع إلى أسبوعين) ⬅️ الآن

الهدف: **كل زيارة يسجلها المندوب تصل للمشرف والمدير.** لا شيء آخر قبل هذا.

1. **إصلاح قاعدة البيانات** — تشغيل `supabase/tips_crm_field_sync_company_id.sql` (جاهز)، ثم اختبار دورة كاملة: مندوب يسجل زيارة → تظهر للمشرف → تظهر للمدير.
2. **توحيد مصدر الحقيقة لقاعدة البيانات** — سحب المخطط المنشور فعلياً (`supabase db pull`) إلى مجلد `supabase/migrations/` واعتماده كمرجع وحيد. حذف ملفات SQL المتفرقة القديمة (أكثر من 50 ملفاً) أو نقلها لأرشيف.
3. **قراءة الزيارات من الخادم** — دالة `tips_crm_list_team_visits` تحترم الصلاحيات (المندوب يرى زياراته، المشرف فريقه، المدير الشركة)، وشاشات المشرف والمدير تقرأ منها.
4. **إظهار الأخطاء الحقيقية** — استبدال الـ 14 موضعاً بـ `describeError` (موجودة في `lib/error-message.ts`).
5. **الأمان العاجل** — تغيير كلمة مرور حسابات الاختبار، نقل الملف خارج المستودع، إضافة مفاتيح Supabase و Resend في hPanel.

**معيار الإنجاز:** مندوب في الميدان يسجل 10 زيارات بدون إنترنت، يتصل، وتظهر الـ 10 عند المشرف خلال دقيقة.

## المرحلة 1 — البنية الهندسية (3–4 أسابيع)

| العمل | لماذا |
|---|---|
| **CI على GitHub Actions**: typecheck + اختبارات + `expo-doctor` + بناء السيرفر لكل push | كل مشكلة واجهناها في البناء كانت ستُكتشف قبل الدفع |
| **فصل اختبارات التكامل** عن اختبارات الوحدة (تُشغّل فقط عند توفر المفاتيح) | الاختبارات الحالية حمراء دائماً بدون مفاتيح، فلا أحد يثق بها |
| **اختبارات صلاحيات قاعدة البيانات (RLS)**: هل يرى مندوب شركة A بيانات شركة B؟ | هذا أخطر خطأ ممكن في منصة متعددة الشركات |
| **تقسيم `lib/crm-store.tsx`** (25 سطراً تتجاوز 500 حرف) إلى وحدات: مزامنة، زيارات، خطط، إشعارات، مع React Query | ملف واحد يحمل كل منطق التطبيق يجعل كل إصلاح مخاطرة |
| **فصل كود الويب عن الهاتف** (`*.web.tsx` / `*.native.tsx`) بدل فحوص `typeof window` | هذا ما أوقف التطبيق لحساب الشركة |
| **مراقبة الأعطال** (Sentry لـ React Native والسيرفر) | الآن نعرف بالعطل فقط عندما يرسل أحد لقطة شاشة |
| **تحديثات OTA** (EAS Update) | إصلاح الواجهة يصل للهواتف في دقائق بدون APK جديد |

## المرحلة 2 — تجربة المندوب الميدانية (4–6 أسابيع)

المندوب هو مصدر كل البيانات؛ إن لم يكن التطبيق سهلاً له، تفشل المنظومة كلها.

1. **وضع عدم الاتصال الكامل** — طابور مزامنة واضح بحالة لكل تقرير (محفوظ / يُرسل / وصل / فشل + السبب + زر إعادة)، ومنع تكرار نفس الزيارة.
2. **التحقق من الموقع** — تسجيل الحضور عند الجهة بالـ GPS مع نطاق مسموح، وتنبيه المشرف عند الزيارة خارج المنطقة.
3. **جدول اليوم** — شاشة واحدة: زيارات اليوم بالترتيب على الخريطة، الزيارة التالية، ما تأخر.
4. **نماذج أسرع** — حقول مسبقة التعبئة من الزيارة السابقة، اختيار الجهة بالبحث، تقليل الحقول الإلزامية.
5. **تسميات واضحة لكل حقل** وتوحيد التصميم (الأزرار، الألوان، الخطوط) عبر مكتبة مكونات واحدة.
6. **إشعارات Push حقيقية** — اعتماد الخطة، تعليق المشرف، تذكير بزيارة متأخرة.

---

## المرحلة 3 — المشرف والإدارة والتحليلات (4–6 أسابيع)

1. **لوحة المشرف على الهاتف** — تغطية الفريق اليوم، من لم يبدأ، الزيارات خارج المنطقة، اعتماد الخطط بضغطة.
2. **لوحة المدير** — نسبة الإنجاز مقابل المستهدف لكل مندوب ومنطقة، التحصيل اليومي، أفضل وأضعف أداء، مع فلاتر بالتاريخ والمنطقة والتخصص.
3. **تقارير قابلة للتصدير** (Excel/PDF) ومجدولة بالبريد أسبوعياً.
4. **خريطة التغطية** — الجهات المزارة وغير المزارة لكل منطقة.
5. **سجل تدقيق** واضح لكل تعديل على الخطط والتحصيلات.

---

## المرحلة 4 — النضج التجاري (مستمر)

1. **النشر على Google Play** (مسار Internal ثم Production) و**App Store**.
2. **الاشتراكات والفوترة** — حدود المستخدمين لكل باقة مطبّقة فعلياً في السيرفر.
3. **دعم اللغتين** (عربي/إنجليزي) والوضع الداكن بنظام ألوان صحيح.
4. **التكامل** — تصدير للأنظمة المحاسبية، Google Sheets (موجود جزئياً)، واجهة API للشركات الكبيرة.
5. **الأداء والتوسع** — فهارس قاعدة البيانات، تقسيم البيانات بالشهر عند تجاوز مئات آلاف الزيارات، نسخ احتياطي واختبار استرجاع.
6. **أمن البيانات** — مراجعة دورية لصلاحيات RLS، تحديث الحزم (59 ثغرة معروفة في `npm audit` حالياً)، سياسة احتفاظ بالبيانات.

## طريقة العمل المقترحة

- **دورات أسبوعين**، كل دورة تنتهي بنسخة يجربها مندوب حقيقي في الميدان.
- **فرع رئيسي محمي** + Pull Request لكل تغيير + CI أخضر قبل الدمج.
- **بيئتان منفصلتان**: تجريبية (staging) وإنتاج، لكل منهما مشروع Supabase خاص — لا تجارب على بيانات الشركات الحقيقية.
- **مقياس نجاح واحد لكل مرحلة** (مثلاً: نسبة التقارير التي تصل خلال دقيقة، عدد الأعطال لكل 1000 جلسة).
