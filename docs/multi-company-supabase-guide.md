# دليل تحويل Tips CRM إلى منصة متعددة الشركات وإدارة مديري النظام

**إعداد: Manus AI**

## 1. النتيجة المطلوبة

المطلوب هو أن تعمل نسخة واحدة من **Tips CRM** لخدمة شركات عديدة، مثل Tips وDef وغيرها، مع عزل كامل للبيانات. أي أن مدير شركة Def يرى المستخدمين والعملاء والخطط والتقارير التابعة لشركة Def فقط، ولا يستطيع رؤية أي بيانات تخص Tips أو أي شركة أخرى.

> في هذا النموذج لا ننشئ تطبيقاً أو مشروع Supabase جديداً لكل شركة. نحتفظ بتطبيق واحد وقاعدة بيانات واحدة، ثم نعزل البيانات باستخدام معرف شركة ثابت وسياسات وصول على مستوى الصفوف (**RLS**).

## 2. الوضع الحالي وما الذي يتغير

المخطط الحالي `tips_crm` يحتوي على الجداول التشغيلية مثل ملفات المستخدمين والمناطق والجهات والخطط والزيارات، لكنه لا يحتوي بعد على مفهوم **الشركة** أو **المنظمة**. لذلك فإن الواجهة الحالية مناسبة لشركة واحدة فقط.

| العنصر | الحالة الحالية | التعديل المطلوب للتعدد المؤسسي |
|---|---|---|
| الشركات | لا يوجد جدول شركات | إنشاء جدول `companies` |
| عضوية المستخدم | `profiles` يحدد الدور فقط | إنشاء جدول `company_memberships` يربط المستخدم بالشركة والدور |
| البيانات التشغيلية | لا يوجد مفتاح شركة | إضافة `company_id` إلى كل جدول تشغيلي |
| الصلاحيات | الدور يطبق على كامل النظام | الدور يطبق داخل الشركة فقط |
| مدير المنصة | غير منفصل عن مدير الشركة | إنشاء `platform_admins` مستقل |

## 3. النموذج الموصى به

أوصي بنموذج **قاعدة بيانات مشتركة مع عزل على مستوى الصفوف**. هو الأنسب عندما تريد استضافة عدد كبير من الشركات بكفاءة، ويقلل كلفة التشغيل والصيانة مقارنة بإنشاء قاعدة بيانات منفصلة لكل شركة.

### الجداول الجديدة

| الجدول | الغرض | أهم الحقول |
|---|---|---|
| `companies` | تعريف كل شركة عميلة | `id`, `name`, `slug`, `is_active`, `plan_key` |
| `company_memberships` | ربط المستخدم بالشركة والدور | `company_id`, `profile_id`, `role_key`, `is_active` |
| `platform_admins` | مديرو منصة Tips CRM ككل | `profile_id`, `is_active` |

### التغيير على الجداول الموجودة

نضيف حقل `company_id` إلى جداول البيانات التي تخص الشركة، ومنها: `profiles` أو جدول العضويات البديل، `territories`، `accounts`، `plans`، `plan_visits`، `visits`، `duty_sessions`، `notifications`، الأهداف، التحصيلات، العينات، الفعاليات، إعدادات البريد وسجل التدقيق.

يجب أن تكون الفهارس المركبة مبنية على `company_id` مع الحقول المستخدمة في البحث، مثل:

```sql
CREATE INDEX accounts_company_name_idx
  ON tips_crm.accounts (company_id, name);

CREATE INDEX plans_company_owner_dates_idx
  ON tips_crm.plans (company_id, owner_id, starts_on);
```

هذه الفهارس تحافظ على سرعة التقارير والبحث حتى عند نمو عدد الشركات والسجلات.

## 4. كيف يمنع النظام خلط البيانات

عند تسجيل الدخول، يحصل المستخدم على معرفه من Supabase Auth. يحدد النظام الشركات التي ينتمي إليها عبر `company_memberships`. ثم تُطبق كل عملية قراءة أو كتابة بشرط أن المستخدم عضو نشط في الشركة المحددة.

المبدأ العملي لسياسة RLS هو:

```sql
USING (
  EXISTS (
    SELECT 1
    FROM tips_crm.company_memberships membership
    WHERE membership.company_id = accounts.company_id
      AND membership.profile_id = auth.uid()
      AND membership.is_active = true
  )
)
```

بهذه الطريقة، حتى إذا حاول مستخدم تغيير رابط أو طلب من المتصفح، فلن يستطيع تجاوز العزل، لأن قاعدة البيانات نفسها ترفض الوصول غير المصرح به. Supabase تصدر رمز وصول مرتبطاً بالمستخدم ويمكن سياسات RLS من فرض الوصول على مستوى الصف، وهي الآلية المناسبة لعزل بيانات الشركات. [1]

## 5. الأدوار المقترحة

| الدور | النطاق | الصلاحيات |
|---|---|---|
| مدير المنصة | جميع الشركات | إنشاء شركة، إيقافها، تعيين مدير شركة، مراقبة عامة بلا تعديل مالي مباشر |
| مدير الشركة | شركة واحدة | إدارة الفريق والمناطق والخطط والتقارير الخاصة بشركته |
| مدير المبيعات | شركة واحدة | اعتماد الخطط وإدارة الفريق التشغيلي |
| مندوب مبيعات | شركة واحدة | خططه وزياراته وبياناته فقط |
| مندوب طبي | شركة واحدة | خططه وزياراته الطبية ومواده المعتمدة فقط |

يمكن لاحقاً السماح لمجموعة شركات بالعمل تحت حساب موحد عبر إضافة أكثر من صف للمستخدم نفسه في `company_memberships`، مع شاشة واضحة لاختيار الشركة الحالية بعد تسجيل الدخول.

## 6. خطة تنفيذ آمنة دون إيقاف النظام

| المرحلة | التغيير | الأثر على المستخدمين |
|---|---|---|
| 1 | إنشاء جداول الشركات والعضويات فقط | لا أثر مباشر |
| 2 | إنشاء شركة افتراضية باسم Tips وربط كل البيانات الحالية بها | لا يتغير سلوك المستخدمين |
| 3 | إضافة `company_id` تدريجياً وفهارس الأداء | قراءة وكتابة مستمرة مع اختبار |
| 4 | تحديث دوال RPC وسياسات RLS والواجهة | يبدأ العزل الفعلي |
| 5 | تفعيل شاشة مدير المنصة وإنشاء الشركة الثانية Def | توسع جاهز للشركات الجديدة |

يُنفذ ذلك بترحيلات صغيرة قابلة للتراجع وبتحقق بعد كل مرحلة. **لا نغير مخطط `public`**؛ كل التغييرات تبقى داخل `tips_crm`.

## 7. إنشاء مدير نظام الآن من لوحة Supabase

### أ. أنشئ حساب الدخول

1. افتح لوحة مشروع Tips CRM في Supabase: `https://app.supabase.com/project/luqrrjhvaremronfcvaf`.
2. من القائمة الجانبية افتح **Authentication** ثم **Users**.
3. اضغط **Add user**.
4. إذا ظهرت لك خيارات الإنشاء، اختر **Create new user** أو **Create user with password**.
5. أدخل البريد الإلكتروني وكلمة مرور مؤقتة قوية لا تقل عن 12 حرفاً، مثل كلمة تحتوي أحرفاً كبيرة وصغيرة وأرقاماً ورمزاً خاصاً.
6. فعّل خيار **Auto Confirm User** أو **Confirm email** إن كان متاحاً، ثم اضغط **Create user**.
7. افتح السجل الذي أنشأته، وانسخ قيمة **User UID** فقط؛ لا تنسخ أو تشارك أي مفاتيح سرية للمشروع.

> تختلف تسمية زر إنشاء المستخدم قليلاً بحسب إصدار لوحة Supabase. إذا وجدت فقط خيار **Send invitation**، فهذا ينشئ دعوة بالبريد ليضبط المستخدم كلمة المرور بنفسه. توثق Supabase مسار الدعوة من صفحة **Authentication → Users → Add user**، كما توضح أن البريد/كلمة المرور مفعّل افتراضياً في المشاريع المستضافة. [1] [2]

### ب. اربط الحساب بدور مدير النظام في Tips CRM

بعد إنشاء المستخدم، افتح **SQL Editor** ثم **New query**. استبدل القيم بين علامات الاقتباس فقط ثم نفذ الاستعلام:

```sql
INSERT INTO tips_crm.profiles (
  id,
  full_name,
  email,
  role_key,
  is_active
)
VALUES (
  'PUT-THE-USER-UID-HERE',
  'اسم المدير الكامل',
  'manager@company.com',
  'system_admin',
  true
)
ON CONFLICT (id) DO UPDATE
SET full_name = EXCLUDED.full_name,
    email = EXCLUDED.email,
    role_key = 'system_admin',
    is_active = true,
    updated_at = now();
```

ثم تحقق من النتيجة بهذا الاستعلام:

```sql
SELECT id, full_name, email, role_key, is_active
FROM tips_crm.profiles
WHERE email = 'manager@company.com'
LIMIT 1;
```

يجب أن تكون النتيجة `role_key = system_admin` و`is_active = true`.

### ج. اختبار المدير

1. افتح تطبيق Tips CRM: `https://tipscrm-vevc4ncu.manus.space`.
2. سجّل الدخول بالبريد وكلمة المرور اللذين أنشأتهما.
3. يجب أن يذهب الحساب إلى بوابة الإدارة.
4. اختبر قراءة قائمة الفريق والمناطق. لا تنشئ مناطق إنتاجية قبل التأكد من أن الحساب صحيح.

## 8. أخطاء يجب تجنبها

| لا تفعل | السبب | البديل الصحيح |
|---|---|---|
| لا تدخل كلمة المرور أو الهاش يدوياً في `auth.users` | يمكن أن يكسر المصادقة أو تأكيد البريد | استخدم Authentication → Users أو خدمة CRM الآمنة |
| لا تستخدم `service_role` في تطبيق الهاتف أو الويب | يتجاوز RLS بالكامل | يبقى على الخادم فقط |
| لا تجعل `system_admin` دوراً لكل موظف | يزيل العزل الإداري | أنشئ مدير شركة أو مدير مبيعات حسب الحاجة |
| لا تنفذ ترحيل التعدد المؤسسي مباشرة على الإنتاج | تغييرات واسعة في الجداول والسياسات | ابدأ بنسخة اختبار وخطة ترحيل مرحلية |

## 9. القرار المقترح

ابدأ الآن بالحل المرحلي: **شغّل Tips CRM لشركة Tips أولاً، وأنشئ فقط مديري الشركة من لوحة الإدارة أو Supabase حسب الإجراء أعلاه**. عندما تكون جاهزاً لإضافة شركة Def، ننفذ حزمة التعدد المؤسسي عبر مراحل مع اختبار كامل؛ لن تحتاج حينها إلى نسخ البرنامج أو إنشاء تطبيق مستقل.
